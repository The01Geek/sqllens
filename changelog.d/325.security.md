Row-level security now blocks two paths around your rules: PostgreSQL child
tables and calls to database functions. With RLS rules configured, SQL Lens
blocks queries that reference a PostgreSQL partition or inheritance child
table, even when a rule names the child: put your rules on the top-level table
and query it, and its rules also filter the rows stored in its children. Move
any rule written for a child table to its parent. Under RLS, calls to
PostgreSQL functions outside `pg_catalog` and `information_schema` (extension
functions included) and calls to MySQL stored functions are blocked; matching
is by name alone, so a built-in call is also blocked when such a function
shares its name. While rules are configured, the read-only guard's function
blocklist (for example `pg_sleep`) now applies even when `database.read_only`
is `false`. SQL Lens checks only names written as calls (`name(...)`): on
PostgreSQL, for example, `SELECT o.order_total FROM orders o` can still call a
function `order_total(orders)`. Keep granting the SQL Lens database user
`EXECUTE` only on functions you have reviewed. See
[Row-Level Security](docs/external/row-level-security.md#limitations).
